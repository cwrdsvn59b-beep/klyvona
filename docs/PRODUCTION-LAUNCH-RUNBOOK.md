# Запуск KLYVONA в production

Дата: 2026-10-22.
Ветка подготовки: `feature/klyvona-pre-neon-final-audit`.
Тикет: T-I7024. Пока он открыт, production-запуск заблокирован.

Этот документ ничего не применяет. Он не заменяет резервную копию и не разрешает Publish.

## Что уже известно локально

В этой рабочей копии нет `DATABASE_URL`, `POSTGRES_URL`, `.env` и `.grok/app-env.json`. Подключение к Neon отсюда не выполнялось.

Приложение использует только переменную `DATABASE_URL`. Другие имена (`POSTGRES_URL`, `NEON_DATABASE_URL`) код не читает.

- Если `DATABASE_URL` задан, [src/lib/db.ts](../src/lib/db.ts) открывает Neon.
- Если переменная пустая, локальная копия и preview могут работать на PGLite в памяти.
- Опубликованное приложение — это процесс с непустым `GROK_PROJECT_ID` или `VERCEL_ENV=production`. Без `DATABASE_URL` оно обязано остановиться и не открывать PGLite. Это правило в [scripts/db-mode.mjs](../scripts/db-mode.mjs).
- `npm run build` вызывает `scripts/migrate.mjs`. Мигратор читает только каталог `migrations/` и записывает имя файла в `_migrations`. Файлы из `docs/sql/` он не видит.
- `1005` и `1006` лежат в `docs/sql/` и в `migrations/` не скопированы. Случайный build их не применит.

Пока колонок и таблиц из `1005`/`1006` нет, платная генерация не начинается:

- `reservePhotoSlot` читает `publishing_jobs.subscription_period_id`. Коды `42P01` и `42703` возвращают `schema_unavailable`. Новое задание при этом не фиксируется, Make не вызывается.
- Если резерв успел записаться, а колонки `dispatch_state` ещё нет, обработчик снимает только невостребованную строку без delivery и отвечает `503 schema_unavailable`. Сетевой вызов не делается.
- `openPaidPeriod` при отсутствии `payment_confirmations` или `subscription_periods` тоже возвращает `schema_unavailable` и не меняет тариф.
- Callback результата при той же ошибке схемы отвечает `503` и не создаёт новую генерацию.

Это уже покрыто локальными тестами. Повторять их на production не нужно.

## Что будет безопасно после ответа

Только после того, как хост, имя базы и роль совпали с опубликованным приложением и снимок создан:

1. Выполнить [docs/sql/READONLY-PRODUCTION-PRECHECK.sql](sql/READONLY-PRODUCTION-PRECHECK.sql) ролью только на чтение.
2. Сверить `_migrations` со списком выше. Не запускать заново уже записанные файлы и не додумывать пропущенную историю.
3. Отдельной явной сессией, не через `npm run build` и не через Publish, применить `docs/sql/1005_subscription_periods.sql`, затем `docs/sql/1006_period_ownership_and_payments.sql`. Оба файла можно выполнить повторно: они используют `if not exists` и не удаляют клиентов.
4. Повторить read-only проверки из раздела ниже.
5. Не копировать `1005` и `1006` в `migrations/`, пока не решено, что следующий build должен увидеть их как уже учтённые. Если скопировать их раньше подтверждения базы, следующий production build применит их к тому `DATABASE_URL`, который подставит платформа.
6. Не включать `MAKE_CONTENT_WEBHOOK_URL`, пока послемиграционные проверки не пройдены и коммерческие решения ниже не приняты.

## Порядок будущего запуска

### 1. Идентификация

Записать вне git: project id, ветка Neon, хост, имя базы, роль, pooled или direct. Сравнить с ответом T-I7024. Если хоть одно поле не совпало, остановиться.

### 2. Резервная копия

Сделать снимок ветки или PITR до первой записи. Записать имя снимка и время. Не считать `pg_dump` с рабочей машины заменой снимка платформы, если поддержка подтвердила только свой механизм.

### 3. Проверка схемы

Запустить read-only файл. Сохранить только счётчики и имена объектов. Не сохранять токены, хеши секретов, подписи и URL изображений.

Остановиться, если:

- база не та;
- в `_migrations` нет ожидаемых `1002`–`1004`, а таблицы результатов уже используются;
- `1005` или `1006` уже применены частично и это не объяснено.

### 4. Миграции 1005 и 1006

Применять вручную, по одному файлу, после снимка. Не выполнять `npm run build`, Publish или `npm run db:migrate` на production ради этих файлов.

`1005` создаёт журнал периодов и не переписывает клиентов. `1006` добавляет пустые `subscription_period_id`, `dispatch_state`, ручные подтверждения оплаты и составные внешние ключи. Старые строки остаются с `NULL`. Приложение не приписывает их к новому периоду и не отправляет их в Make повторно.

### 5. Проверка данных

Сразу после применения снова выполнить read-only запросы. Счётчики клиентов, заданий и результатов не должны уменьшиться. Число строк с пустым `subscription_period_id` должно совпасть с числом строк, которые существовали до колонки. Новых строк `payment_confirmations` быть не должно: миграция их не создаёт.

### 6. Контроль приложения

Не менять webhook Make и не публиковать приложение в этом шаге. На запросе фото до появления колонок ответ уже `503` и код `schema_unavailable`. После появления колонок тот же запрос сможет создать задание и, если webhook включён, вызвать Make. Поэтому webhook остаётся выключенным, пока не приняты решения ниже.

Проверка без генерации: один авторизованный запрос статуса или чтение профиля администратора. Не нажимать создание фото и не слать тестовый callback на production URL.

### 7. Откат

Комментарии `DROP` внизу `1005` и `1006` безопасны только для пустой черновой схемы. После реальных платежей, заданий или результатов удаление таблиц уничтожает данные. Откат production — это восстановление снимка из шага 2, затем проверка, что приложение смотрит на восстановленную базу. Не делать `DROP` на боевых таблицах.

## Обязательные проверки после миграций

Их не запускать сейчас. После применения, только на подтверждённой базе:

1. `current_database()` и хост совпадают с записью из T-I7024.
2. В `_migrations` по-прежнему есть `1002`, `1003` и `1004`. `1005` и `1006` могут отсутствовать в этой таблице, если их применили вручную из `docs/sql/`. Это нормально, пока их не перенесли в `migrations/`.
3. Существуют `subscription_periods`, `payment_confirmations`, `quota_reconciliations`.
4. У `publishing_jobs` и `instagram_generation_results` есть `subscription_period_id`, у `webhook_deliveries` есть `dispatch_state`.
5. Есть ограничение `payment_confirmations_amount_chk` и уникальный индекс `payment_confirmations_payment_id_idx`.
6. Есть составные ключи периода и результата на пару `(id, client_id)`.
7. Число клиентов, заданий и результатов не уменьшилось.
8. Все старые задания и результаты, которые были до колонки, имеют `subscription_period_id is null`.
9. Нет строки delivery с пустым `dispatch_state`, которую приложение собралось отправить повторно. Такие строки остаются резервом.
10. Запрос платной генерации при выключенном webhook не уходит в сеть. Пока webhook выключен, отсутствие URL — это `never_attempted`, а не повторная платная попытка.
11. Смена статуса подписки в админке не создаёт `subscription_periods` и не пишет `payment_confirmations`.
12. Открытие платного периода без сессии администратора, без суммы 600 ILS или с чужим `payment_id` не создаёт период.

## Коммерческие решения, которые код не меняет

Эти правила сейчас зафиксированы и не расширяются этим документом.

| Вопрос | Как код ведёт себя сейчас | Что нужно решить отдельно |
| --- | --- | --- |
| Продление | Второй подтверждённый платёж при открытом платном периоде записывается без периода и возвращает `renewal_blocked`. Действующий срок не отменяется и не продлевается. | Когда можно открыть следующий месяц и что делать с остатком дней. |
| Ручная оплата | 600 ILS принимает только администратор. Источник — `admin_attestation`, не банк. Сумма и валюта проверяются в коде и ограничением таблицы. | Какой провайдер и какой внешний идентификатор платежа заменят ручную отметку. |
| Неизвестный расход Make | `attempted_unknown`, пустой `dispatch_state` у существующей delivery и `confirmed_not_started` не возвращают квоту и не запускают вторую генерацию. | Кто и по какому доказательству может списать или вернуть этот слот. Компенсацию код не придумывает. |
| Праздники Израиля | Рабочие дни — воскресенье–четверг, календарь `Asia/Jerusalem`. Праздники не вычитаются. | Какой официальный календарь использовать и кто его обновляет. |

До этих решений не включать автоматическую публикацию и не считать ручную отметку 600 ₪ банковским поступлением.
