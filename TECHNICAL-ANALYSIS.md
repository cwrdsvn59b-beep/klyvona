## 2. Что добавлено

Реализован серверный OAuth Meta для страницы Facebook и связанного профессионального Instagram. Пока нет полной конфигурации, обработчики отвечают HTTP 503 и не создают успешное подключение.

TikTok по-прежнему отвечает 503. Обмен кода TikTok не написан.

Автоматическая публикация постов не включалась. Очередь `publishing_jobs` по-прежнему только хранит статус. Сценарии Make не менялись. Вебхук Make по-прежнему получает только идентификатор, номер заявки и статусы, без контактов и без токенов.

## 3. Поток подключения

Клиент сначала завершает онбординг. Сервер создаёт длинный одноразовый секрет подключения, сохраняет только его SHA-256 и отдаёт исходное значение один раз в ответ браузеру. Браузер держит его в `sessionStorage` вместе с номером заявки. Номера заявки одного недостаточно: им нельзя начать OAuth.

Дальше, на странице `/connect`:

1. Браузер отправляет `POST /api/oauth/facebook/start` или `POST /api/oauth/instagram/start` с номером заявки и секретом подключения. Секрет не кладётся в адресную строку.
2. Если конфигурация неполная, ответ 503 и поле `oauthActivated: false`. Перехода на Facebook нет.
3. Если конфигурация полная, сервер записывает одноразовый state на 10 минут, ставит cookie `klyvona_meta_oauth` с `HttpOnly` и `SameSite=Lax` и возвращает адрес диалога Meta. Секрет приложения в этот адрес не входит.
4. Meta возвращает браузер на callback с `code` и `state`.
5. Сервер проверяет cookie, идентификатор state, хэш nonce, срок, платформу и то, что state ещё не использован. Затем сразу помечает state использованным.
6. Код обменивается на короткий токен пользователя, затем на длинный токен. Запросы к Meta идут `POST` с телом формы, не со секретом в адресе.
7. `GET /me/accounts` запрашивает страницы, задачи и связанный `instagram_business_account`. Токен передаётся заголовком `Authorization`, не параметром адреса.
8. Подходящие учётки записываются во временную таблицу на 15 минут. Токен в браузер не возвращается.
9. Клиент на `/connect` выбирает только строку, которая принадлежит его заявке и помечена как допустимая.
10. Сервер копирует уже зашифрованный токен в `social_accounts` этой заявки.

Отключение обнуляет ciphertext, срок, внешний идентификатор и возвращает статус `awaiting_setup`. Чужую строку так обнулить нельзя: запрос снова проверяет секрет подключения.

Обновление токена, где Meta это поддерживает, вызывает `grant_type=fb_exchange_token` для сохранённого длинного токена пользователя и заново читает токен той же страницы. Если страница исчезла или Meta отклонила токен, статус становится `expired`, а текст ошибки говорит подключить заново. Сам отклонённый токен в ответ и в лог не пишется.

## 4. Meta API

Версия взята из журнала Graph API: последняя стабильная на 29 июля 2026 — **v26.0**. Версия v21.0 из старого каркаса больше не используется. v21.0 ещё не была помечена устаревшей, но текущий код её не вызывает.

Адреса:

- диалог: `https://www.facebook.com/v26.0/dialog/oauth`
- токен: `https://graph.facebook.com/v26.0/oauth/access_token`
- страницы: `https://graph.facebook.com/v26.0/me/accounts`

Разрешения, которые запрашивает код:

| Разрешение | Зачем |
|---|---|
| `pages_show_list` | список страниц, которыми человек может управлять |
| `pages_manage_posts` | публикация на страницу Facebook |
| `pages_read_engagement` | чтение, которое Pages API требует рядом с публикацией |
| `instagram_basic` | профессиональный Instagram, связанный со страницей |
| `instagram_content_publish` | публикация в этот Instagram |

`business_management` не запрашивается. По документации Meta он нужен системному пользователю Business Manager, а не человеку, который публикует на свою страницу.

Допустимая страница Facebook: в `tasks` есть `CREATE_CONTENT`, `MANAGE`, `PROFILE_PLUS_CREATE_CONTENT` или `PROFILE_PLUS_FULL_CONTROL`.

Допустимый Instagram: у страницы есть `instagram_business_account` и та же правовая задача. Личный Instagram без профессиональной связи показывается как недопустимый и не сохраняется с токеном.

Это путь Instagram API with Facebook Login. Отдельный Instagram Login не реализован, потому что публикация в этой модели идёт через страницу Facebook и токен страницы.

## 5. Точные callback

Их нужно вписать в Meta → Facebook Login → Valid OAuth Redirect URIs без завершающего слэша:

- `https://spring-orbit-honey-baker.grok.me/api/oauth/facebook/callback`
- `https://spring-orbit-honey-baker.grok.me/api/oauth/instagram/callback`

В проде origin берётся из `META_OAUTH_REDIRECT_ORIGIN`, а если её нет — из `BETTER_AUTH_URL`. Если приложение опубликовано и нет ни того ни другого, callback не строится и ответ будет 503. Адрес из заголовка запроса в проде не используется: платформа может подменить его на внутренний хост.

## 6. Защита

| Контроль | Как сделано |
|---|---|
| Нет самоназначения администратора | без изменений: только `KLYVONA_ADMIN_EMAILS` и подтверждённая почта |
| State | 32 случайных байта, в базе только SHA-256, срок 10 минут |
| CSRF | cookie должна совпасть с идентификатором state |
| Одноразовость | `update ... where used_at is null` |
| Привязка к клиенту | state и временные учётки хранят `client_id` заявки, найденной по секрету |
| Чужой выбор | `selectionAllowed` сравнивает владельца и заявку |
| Секрет приложения | только `process.env`, в браузер и в репозиторий не попадает |
| Токен в покое | AES-GCM, ключ `TOKEN_ENCRYPTION_KEY`, 32 байта в base64 |
| Нет ключа | шифрование бросает ошибку, callback не сохраняет открытый токен |
| Нет базы в проде | `productionDatabaseProblem` закрывает Meta OAuth вместе с остальным продом |
| Логи | пишется код ошибки, не тело токена |
| Make | payload онбординга не расширялся токенами |

Админка по-прежнему читает платформу, статус, текст ошибки и срок. Столбец `token_ciphertext` она не выбирает.

## 7. База

Новая миграция `migrations/0003_meta_oauth.sql` ничего старого не удаляет и не переписывает.

- у `clients` добавляется пустой столбец `connect_secret_hash`
- таблица `oauth_states`
- таблица `oauth_pending_accounts`

Токен постоянного подключения остаётся в уже существующем `social_accounts.token_ciphertext`. На клиента и платформу по-прежнему одна строка. Клиент выбирает одну страницу Facebook и один Instagram.

Старые заявки без хэша секрета подключить нельзя. Секрет выдаётся только новым завершениям онбординга.

В превью без `DATABASE_URL` по-прежнему возможен PGLite. В опубликованном процессе без `DATABASE_URL` PGLite не открывается, и Meta OAuth тоже остаётся закрыт.

## 8. Когда поток остаётся закрыт

Ответ 503, без перехода на Facebook, если отсутствует хотя бы одно из следующего:

- `META_APP_ID`
- `META_APP_SECRET`
- годный `TOKEN_ENCRYPTION_KEY`
- в проде `DATABASE_URL`
- в проде публичный origin (`BETTER_AUTH_URL` или `META_OAUTH_REDIRECT_ORIGIN`)

Успешное подключение кодом не имитируется. Тесты не ходят в Graph API.

## 10. Что нужно сделать вручную

Эти значения не лежат в репозитории.

1. В приложении Meta включить Facebook Login и Instagram API with Facebook Login.
2. Вписать оба callback из раздела 5.
3. В серверные секреты опубликованного приложения добавить `META_APP_ID` и `META_APP_SECRET`.
4. Добавить `TOKEN_ENCRYPTION_KEY`: 32 случайных байта, закодированных в base64.
5. Не вводить `DATABASE_URL` руками, если его подставляет Grok. Без него новая сборка в проде не откроет память и не включит OAuth.

7. Пройти App Review для пяти разрешений. До одобрения войти смогут только роли самого приложения Meta.
